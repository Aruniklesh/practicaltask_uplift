# Requirement Traceability Matrix

Independently derived from the client's original `README.md` (rules R1–R8) and from direct
inspection of `contribution-app/index.html`. "Test Coverage" distinguishes **UI-level**
coverage (exercised through the real rendered page, as a user would experience it) from
**utility-level** coverage (exercised only against the independent Java reference engine,
`CalculationUtils`, which does not prove the real app behaves correctly).

## Coverage Summary

- **Fully covered (UI-level, real app behavior proven):** R1 (all 4 frequencies, exact form), R2 (Members table only), R3, R4, R5 (fixture values), R7 (fixture values), R8 (all defined sub-cases).
- **Partially covered:** R2 on the Calculator (architecturally impossible, now documented instead of silently assumed), R6/R7 at boundary values absent from the fixture (utility-level only).
- **Not covered / Not applicable given current constraints:** R6/R7 boundary values that don't exist in `data/members.json` cannot be proven against the live UI without either modifying client-owned fixture data (not permitted) or the client exposing the order-rounding logic as a callable function (not something this project can request).
